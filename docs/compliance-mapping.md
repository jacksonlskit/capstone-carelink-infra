# Hard-constraint compliance mapping (CareLink Health, Use Case B)

*Status as of 23 Nov 2026, checked against the live environments. First drafted by Jon (SRE) on 25 Oct. **Status is honest, not aspirational**: the brief says "it works" is not a defence against "it violates the constraint", so every row says how to prove it live. Owners of open items are in brackets.*

**Status legend:** **Met** = built and verified live. **Met in code** = built; the live proof is still pending (for example a maintenance window). **Partial** = some of it. **Gap** = not built yet. Labels such as A1 or C2 are the IDs from the team's 25 Oct code review.

| Encrypted at rest: node disks | Terraform launch template (`eks.tf`): root volume `encrypted = true` with the `ebs` key; IMDSv2 required | **Met** (21 Nov: all node volumes encrypted) | `aws ec2 describe-volumes --filters Name=tag:eks:cluster-name,Values=carelink-staging-eks --query 'Volumes[].[VolumeId,Encrypted,KmsKeyId]'` |

| Database not publicly accessible | `publicly_accessible = false`; private DB subnets; the security group allows the DB port only from the private subnets (`rds.tf`) | **Met** | Failed connection from the internet; security group rules |

## Constraint 3: Recovery (RPO <= 24 h, RTO <= 4 h, automated backups, demonstrated restore)

| Requirement | Design decision and where | Status | Evidence to show live |
|---|---|---|---|
| Automated backups | `backup_retention_period = 7`, `backup_window = 17:00-18:00 UTC` (01:00-02:00 SGT), `copy_tags_to_snapshot` (`rds.tf`) | **Met** | `describe-db-instances` -> `BackupRetentionPeriod: 7`, `LatestRestorableTime` |
| RPO <= 24 h | Daily backup plus point-in-time recovery: a realistic RPO of minutes; production Multi-AZ adds a synchronous standby (ADR 0004) | **Met** (21 Nov: latest restorable time about 5 minutes old) | `LatestRestorableTime` within minutes of now |
| RTO <= 4 h | Failover (minutes) or restore from backup; runbook `docs/sre/runbooks/db-instance-failure.md` with a timed drill | **Met** for the restore step: staging drill on 22 Nov restored to `available` in 14 min 48 s and verified the data in 18 min 54 s, about 19 of the 240 minutes; application cutover not timed yet [Jon, Krisna] | Drill record table, section 6 of `docs/sre/runbooks/db-instance-failure.md` |
| **Demonstrate a restore** (staging acceptable) | Take a manual snapshot, restore it to a new instance, verify the data (staging uses `skip_final_snapshot`, and automated backups vanish if the instance is destroyed: A6) | **Met**: point-in-time restore of staging MySQL on 22 Nov (15:51 UTC, CloudTrail `RestoreDBInstanceToPointInTime`, instance `carelink-staging-mysql-drill`, since removed) with `scripts/restore-drill.sh`; row counts match the source (owners 15, pets 13, vets 6, visits 4), timings recorded [Jon, Krisna] | Restore command output, timings, row-count check against the source, in the drill table of `docs/sre/runbooks/db-instance-failure.md` |
| Notice a database failure quickly | RDS CPU, storage and memory alarms and an RDS event subscription in both environments (`monitoring.tf`). Staging alarms reach Discord (SNS to the Discord Lambda). Production: the same bridge is subscribed to `carelink-production-alerts` since 22 Nov (infra PR #78) and its webhook secret is set; a test message ran the Lambda without errors, delivery to Discord still to be confirmed | **Met in staging**; **Partial in production** until the Discord message is confirmed [Jon] | Alarm list; Discord message from a test alarm |

## What to say when a gap is asked about
Name the gap before the panel does, state the owner, and say what you would do and how you would prove it: that scores better than a confident wrong answer, per the brief.
