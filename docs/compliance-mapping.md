# Hard-constraint compliance mapping (CareLink Health, Use Case B)

*Status as of 22 Nov 2026, checked against the live environments. First drafted by Jon (SRE) on 25 Oct. **Status is honest, not aspirational**: the brief says "it works" is not a defence against "it violates the constraint", so every row says how to prove it live. Owners of open items are in brackets.*

**Status legend:** **Met** = built and verified live. **Met in code** = built; the live proof is still pending (for example a maintenance window). **Partial** = some of it. **Gap** = not built yet. Labels such as A1 or C2 are the IDs from the team's 25 Oct code review.

## Constraint 1: Availability 99.9% in clinic hours (08:00-20:00 SGT), no single point of failure, survive loss of one application instance

| Requirement | Design decision and where | Status | Evidence to show live |
|---|---|---|---|
| Targets and measurement | SLIs and SLOs in `docs/sre/slo-and-alerting.md` (99.9% in clinic hours = 21.6 min per 30 days; p95 latency). Staging: Prometheus records them from the external probe (`carelink:staging:probe_success:ratio`, `carelink:staging:probe_latency:p95`) with fast and slow burn-rate alerts. Production: the same rules exist but need a production probe target; the CloudWatch ALB burn-rate alarms in `monitoring.tf` are switched off (`monitor_alb = false`) | **Met in staging**; **Partial in production** [SRE: Shilpa, Jon] | Prometheus query of the recording rules (21 Nov: availability ratio 1.0, p95 34 ms); alert rule list |
| Multi-AZ network | VPC with 3 public + 3 private subnets over 3 AZs (`vpc.tf`) | **Met** | `aws ec2 describe-subnets --filters Name=vpc-id,Values=<vpc>` showing 3 AZs |
| Nodes spread across AZs | Managed node group over all 3 private subnets; both environments `min_size = 3`, `desired_size = 4`, `max_size = 6` (`eks.tf`). Sized from measured use (20 Nov): memory and pod slots limit, not CPU (3-11% used); 4 nodes keep production N+1 | **Met**: 4 nodes span all 3 private subnets | `kubectl get nodes -L topology.kubernetes.io/zone` |
| 2+ replicas per service on different nodes | App chart (`charts/carelink` in the app repo): 2 replicas per service, topology spread over nodes (hard) and zones (preferred), PodDisruptionBudget `minAvailable: 1` | **Met** (21 Nov: each service's 2 production pods on different nodes and zones) | `kubectl -n production get pods -o wide`; `kubectl -n production get pdb` |
| Database tier survives an instance/AZ loss | `multi_az = local.is_prod && each.value.multi_az_in_production` (`rds.tf`); `true` for the app's MySQL, so production keeps a synchronous standby in another AZ; staging stays single-AZ (cost) | **Met in code** (A1 closed): production converts in the maintenance window of Sun 22 Nov (18:30-19:30 UTC), then rehearse a forced failover [Krisna] | `aws rds describe-db-instances --query 'DBInstances[].[DBInstanceIdentifier,MultiAZ,SecondaryAvailabilityZone]'` |

| Public entry point | ALB from the app's Ingress (`charts/carelink/templates/ingress.yaml`) via the AWS Load Balancer Controller (`lbc.tf`); hostname `carelink-<env>.sctp-sandbox.com` kept on the current ALB by external-dns (`dns.tf`); health check `/readyz` | **Met** in both environments | https://carelink-production.sctp-sandbox.com; ALB target health `healthy` |

## Constraint 2: Data protection (encrypted at rest and in transit, database not public, production access restricted and logged)

| Requirement | Design decision and where | Status | Evidence to show live |
|---|---|---|---|
| Encrypted at rest: database | `storage_encrypted = true` with the `rds` KMS key; master secret encrypted with the `secrets` key (`rds.tf`); key rotation on | **Met** (21 Nov: `StorageEncrypted: true` on every instance) | `describe-db-instances` -> `StorageEncrypted`, `KmsKeyId`; key rotation status |
| Encrypted at rest: node disks | Terraform launch template (`eks.tf`): root volume `encrypted = true` with the `ebs` key; IMDSv2 required | **Met** (21 Nov: all node volumes encrypted) | `aws ec2 describe-volumes --filters Name=tag:eks:cluster-name,Values=carelink-staging-eks --query 'Volumes[].[VolumeId,Encrypted,KmsKeyId]'` |
| Encrypted at rest: Kubernetes volumes | Default StorageClass `gp3-encrypted` with the `ebs` key (`ebs-csi.tf`); the CSI driver role may use that key. The staging monitoring volumes (Prometheus, Loki, Grafana) were recreated on it after deployment; before that they were unencrypted `gp2` | **Met** once the 22 Nov migration has run [Jack] | `aws ec2 describe-volumes` for the PVC volumes: `Encrypted: true`, `KmsKeyId` = the `ebs` key |
| Encrypted at rest: logs, alerts, state | KMS key on log groups and SNS (`monitoring.tf`); S3 state bucket encryption and versioning (`oicd-bootstrap`) | **Met** | Log group `kmsKeyId`; SNS `KmsMasterKeyId` |
| Encrypted in transit: users to service | HTTPS with a DNS-validated ACM certificate (`oicd-bootstrap/main.tf`, kept there because certificates survive the nightly cleanup), policy `ELBSecurityPolicy-TLS13-1-2-2021-06` (TLS 1.2/1.3 only), HTTP 301 to HTTPS | **Met** in both environments (21 Nov: both ALB listeners on that policy) | Browser padlock; `curl -I http://carelink-production.sctp-sandbox.com` returns 301; `aws elbv2 describe-listeners` |
| Encrypted in transit: app to database | MySQL parameter group with `require_secure_transport = ON` (`rds.tf`); the app connects with `sslMode=REQUIRED` (`app-database.tf`); credentials from the RDS-managed secret through External Secrets. The unused Postgres instances keep the default group | **Met for MySQL** (21 Nov: parameter groups `in-sync`, value 1); certificate identity not verified yet (`VERIFY_IDENTITY` is the next step) | `scripts/test-db-persistence.sh <env> --tls` (app repo): connection without TLS refused, `Ssl_version TLSv1.3` with TLS |
| Database not publicly accessible | `publicly_accessible = false`; private DB subnets; the security group allows the DB port only from the private subnets (`rds.tf`) | **Met** | Failed connection from the internet; security group rules |
| Access to production data **restricted** | Master credential in Secrets Manager (no password in code or state). Cluster access per environment in code (`cluster_access` in `variables.tf`, `eks.tf`): in production only the DevOps owner and the pipeline role are cluster admins, the other team members are view-only (`AmazonEKSViewPolicy`: no Secrets), and this list only changes through a reviewed PR. Still open: the CI production role has AdministratorAccess; no per-person DB users; every cohort member has AdministratorAccess in the shared account (ADR 0006) | **Partial**: Kubernetes access restricted in production; AWS-level access limited by the shared account [Jack] | `aws eks list-associated-access-policies --cluster-name carelink-production-eks --principal-arn <user>` (ClusterAdmin only for the owner, View for the rest); a teammate's `kubectl -n production get secrets` is forbidden |
| Access **logged** (data plane) | DB audit logging is not enabled (only `error` and `slowquery` logs are exported) (A2). Production database changes wait for the maintenance window | **Gap** [Krisna] | Audit log group showing a connection or query event |
| Access **logged** (control plane) | CloudTrail Event history (always on, 90 days) records AWS API calls, including every secret read; EKS control-plane logs, including `audit`, go to CloudWatch in both clusters. Not built: our own trail and the CloudTrail alarms (`monitor_cloudtrail`); the control-plane log groups have no retention set | **Partial**, demonstrable (21 Nov: 23 reads of the DB secret recorded in 2 hours) [Jack] | `aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=GetSecretValue`; `aws eks describe-cluster --name <cluster> --query cluster.logging` |
| Data residency (PDPA) | Deployed in **us-east-1** by team decision for the capstone (synthetic data only); ADR 0007 states the production-intent position | **Accepted limitation**, documented | ADR 0007; `aws_region` in `variables.tf` |

## Constraint 3: Recovery (RPO <= 24 h, RTO <= 4 h, automated backups, demonstrated restore)

| Requirement | Design decision and where | Status | Evidence to show live |
|---|---|---|---|
| Automated backups | `backup_retention_period = 7`, `backup_window = 17:00-18:00 UTC` (01:00-02:00 SGT), `copy_tags_to_snapshot` (`rds.tf`) | **Met** | `describe-db-instances` -> `BackupRetentionPeriod: 7`, `LatestRestorableTime` |
| RPO <= 24 h | Daily backup plus point-in-time recovery: a realistic RPO of minutes; production Multi-AZ adds a synchronous standby (ADR 0004) | **Met** (21 Nov: latest restorable time about 5 minutes old) | `LatestRestorableTime` within minutes of now |
| RTO <= 4 h | Failover (minutes) or restore from backup; runbook `docs/sre/runbooks/db-instance-failure.md` with a timed drill | **Not yet proven**: drill not run [Jon, Krisna] | Drill record table filled in with real timestamps |
| **Demonstrate a restore** (staging acceptable) | Take a manual snapshot, restore it to a new instance, verify the data (staging uses `skip_final_snapshot`, and automated backups vanish if the instance is destroyed: A6) | **Not done** [Jon, Krisna] | `restore-db-instance-from-db-snapshot` output, timings, row-count check |
| Notice a database failure quickly | RDS CPU, storage and memory alarms and an RDS event subscription in both environments (`monitoring.tf`). Staging alarms reach Discord (SNS to the Discord Lambda); the production SNS topic has no subscriber yet | **Met in staging**; **Partial in production** [SRE] | Alarm list; Discord message from a test alarm |

## What to say when a gap is asked about
Name the gap before the panel does, state the owner, and say what you would do and how you would prove it: that scores better than a confident wrong answer, per the brief.
