# Runbook: Grafana admin password

## How the login is stored

| Where | What |
|---|---|
| Secrets Manager `carelink-<env>-grafana-admin` | The source of truth: `admin-user` and `admin-password`. Created and tagged by Terraform (`infra/observability-grafana.tf`), encrypted with the `secrets` KMS key. The first value is generated by Secrets Manager during the first deploy. |
| Kubernetes Secret `grafana-admin` (namespace `monitoring`) | A copy made by External Secrets every 5 minutes (`observability/secrets/grafana-admin.yaml`). |
| Grafana's own database (on its persistent disk) | Grafana saves the admin password there **the first time it starts** and ignores later changes to the secret. |

Because of that last row, a new value in Secrets Manager needs a **one-time reset** inside Grafana. Until then the new password is refused, and the dashboard and data-source sidecars (which log in with the same secret) get `401`. Their failed logins also lock the `admin` user for about 5 minutes (see step 5).

## When to run it

- Once after `infra/observability-grafana.tf` is first deployed (the hand-made secret it replaces was deleted by the nightly cleanup on 14–15 Nov 2026).
- After every rotation (below).
- Not after a normal morning recovery: the secret survives the cleanup and keeps its value.

Grafana runs in staging only for now. Point `kubectl` at the staging cluster first:

```bash
aws eks update-kubeconfig --name carelink-staging-eks --region us-east-1
```

## Steps

1. **The secret has a value.** Prints the version's labels, not the value. Expect `[["AWSCURRENT"]]`.
   ```bash
   aws secretsmanager list-secret-version-ids --secret-id carelink-staging-grafana-admin --query 'Versions[].VersionStages'
   ```

2. **Copy it into Kubernetes now** instead of waiting up to 5 minutes. Expect `SecretSynced` and `True`.
   ```bash
   kubectl -n monitoring annotate externalsecret grafana-admin force-sync="$(date +%s)" --overwrite
   kubectl -n monitoring get externalsecret grafana-admin
   ```

3. **Restart Grafana** so it reads the new value. Delete the pod rather than `rollout restart`: Grafana's disk can attach to one node only, and a rolling restart can leave the new pod waiting for it forever.
   ```bash
   kubectl -n monitoring delete pod -l app.kubernetes.io/name=grafana,app.kubernetes.io/instance=kube-prometheus-stack
   kubectl -n monitoring rollout status deployment/kube-prometheus-stack-grafana
   ```

4. **Reset the password stored in Grafana's database** to the secret's value. The password stays inside the container: it is read from the container's environment and passed on stdin. Expect `Admin password changed successfully`.
   ```bash
   kubectl -n monitoring exec deploy/kube-prometheus-stack-grafana -c grafana -- sh -c 'printf "%s" "$GF_SECURITY_ADMIN_PASSWORD" | grafana cli admin reset-admin-password --password-from-stdin'
   ```

5. **Check the login** without printing the password. Expect `LOGIN OK`.
   ```bash
   kubectl -n monitoring exec deploy/kube-prometheus-stack-grafana -c grafana -- sh -c 'auth=$(printf "%s:%s" "$GF_SECURITY_ADMIN_USER" "$GF_SECURITY_ADMIN_PASSWORD" | base64 | tr -d "\n"); if wget -q -O /dev/null --header "Authorization: Basic $auth" http://localhost:3000/api/user; then echo "LOGIN OK"; else echo "LOGIN FAILED"; fi'
   ```

   **`LOGIN FAILED` right after step 4?** Check why before changing anything. This counts Grafana's "blocked" messages from the last 10 minutes:
   ```bash
   kubectl -n monitoring logs deploy/kube-prometheus-stack-grafana -c grafana --since=10m | grep -c "temporarily blocked"
   ```
   A number above `0` means Grafana's brute-force protection has locked the `admin` user. Between steps 3 and 4 the sidecars tried the new password 5 times while the database still held the old one, and 5 failed logins within 5 minutes lock the user. The lock lifts 5 minutes after the 5th failure, and until then even the correct password gets `401`. Wait 5 minutes and run step 5 again. Don't reset the password again (it changes nothing) and don't turn the protection off. Seen on staging on 15 Nov 2026: failures at 08:46:27, `LOGIN OK` at 08:51:42.

To sign in from a laptop: `kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80`, open http://localhost:3000, user `admin`. This works for the whole team in both environments: in production the view-only users may port-forward in the `monitoring` namespace only (Role `monitoring-portforward`, `infra/eks.tf`). Read the password only when needed, and don't paste it anywhere:

```bash
kubectl -n monitoring get secret grafana-admin -o jsonpath='{.data.admin-password}' | base64 -d; echo
```

View-only users can't read Kubernetes Secrets in production, so read it from Secrets Manager instead (`<env>` is `staging` or `production`):

```bash
aws secretsmanager get-secret-value --secret-id carelink-<env>-grafana-admin --query SecretString --output text | python3 -c 'import json,sys; print(json.load(sys.stdin)["admin-password"])'
```

## Rotate the password

Generate a new value with Secrets Manager and store it, without the password ever reaching the screen or the shell history:

```bash
umask 077; f=$(mktemp); printf '{"admin-user":"admin","admin-password":"%s"}' "$(aws secretsmanager get-random-password --password-length 32 --exclude-punctuation --query RandomPassword --output text)" >"$f"; aws secretsmanager put-secret-value --secret-id carelink-staging-grafana-admin --secret-string "file://$f" >/dev/null; rm -f "$f"
```

Then run steps 2 to 5.

## Why the value is not generated by Terraform

The nightly cleanup deletes the Terraform state, and the morning recovery re-imports every resource. Importing a secret version copies its value into the state file, which everyone in the AWS account can read. So Terraform manages only the secret itself, and the value is written by the pipeline (`terraform_data.grafana_admin_first_value`), which does nothing once the secret has a value.
